● Short answer: vLLM can, but your code currently can't — it scores the two 
  adapters in two sequential passes. Here's the precise picture.

  What vLLM supports

  vLLM's continuous batching allows per-request LoRA: each request in a batch
  can carry its own LoRARequest, and as long as the distinct adapters fit within
  max_loras, they're served concurrently in the same GPU batch. You have
  ROLLOUT_MAX_LORAS=3 (actor=base-policy + anchor + replay), so there's
  physically room for anchor and replay to be active simultaneously.

  What your code actually does — two serial passes

  _tafr_compute_anchor_and_replay_log_probs calls
  _tafr_compute_vllm_log_probs(batch, "anchor") then
  _tafr_compute_vllm_log_probs(batch, "replay") back-to-back. Each call:
  1. load_tafr_lora_adapters(payload, adapters=(adapter,)) — loads one adapter
  (L1727), then
  2. fans the sequences out with asyncio.gather (llm_server.py:232–247).

  So within a single adapter, all sequences are already batched concurrently —
  but anchor and replay are serialized into two separate prefill sweeps.

  Two things block doing them in one sweep:
  - Loading is one-at-a-time (adapters=(adapter,)).
  - The per-server scorer hardcodes a single LoRA slot. score_tafr_logprobs
  (vllm_async_server.py:622) builds LoRARequest(lora_name=VLLM_LORA_NAME, 
  lora_int_id=VLLM_LORA_INT_ID, ...) — it validates adapter via
  tafr_vllm_adapter_spec(adapter) (L613) but then ignores it and reuses the same
  int_id. So anchor and replay are effectively swapped through one slot, which
  inherently prevents co-batching them.

  Note your vllm_scoring.py already defines distinct int_ids — tafr_anchor=124,
  tafr_replay=125 — so the design intended separate slots; the per-request path
  just doesn't use them.

  To score both LoRAs at once

  The change is moderate, not architectural:
  1. Load both adapters concurrently under their own int_ids (124/125) — call
  load_tafr_lora_adapters(payload, adapters=("anchor","replay")) once.
  max_loras=3 already permits it.
  2. Make the per-server scorer honor adapter: build the LoRARequest from
  tafr_vllm_adapter_spec(adapter) (its .int_id / .name) instead of the hardcoded
  VLLM_LORA_INT_ID.
  3. Submit anchor + replay requests in one asyncio.gather (interleaved, each
  tagged with its adapter) so vLLM's continuous batcher runs them together — one
  prefill sweep over 2× the rows instead of two sweeps.

  Expected payoff: roughly collapses two prefill passes into one (~2× on the
  anchor/replay scoring segment), since prefill is throughput-bound and a single
  larger batch amortizes launch/scheduling overhead better than two
  adapter-swapped passes. It won't help if you're memory-bound at high KV
  utilization — but you score right after gen with vLLM still warm, so there's
  usually headroom.

  One caveat worth confirming first: whether your vLLM build applies different 
  LoRAs to different requests within the same forward step efficiently (it does
  for decode; prefill with mixed adapters is also supported but the kernels
  batch per-adapter internally). The win is real but is "one scheduling pass /
  better overlap," not literally "two matmuls fused into one."

❯ why after 4th step? why not from the beginning?                               

● Great question — and the answer is: it's not a fundamental requirement, it's 
  just where the sync is currently wired. The vLLM path could run from step 1;
  nobody hooked it into startup.

  Here's the actual mechanism. The vLLM scoring path requires the anchor/replay
  LoRA adapters to be exported from the FSDP actor and loaded into the vLLM 
  engine. That export+load happens in _tafr_sync_vllm_adapters(), and that
  function is only called inside the checkpoint-and-refresh branch
  (ray_trainer.py:1253), which is gated by should_checkpoint_and_refresh(...) →
  fires every TAFR_CHECKPOINT_INTERVAL steps. So:

  - Before the first sync: tafr_vllm_adapters_ready = False →
  _tafr_can_score_with_vllm() returns False → HF path.
  - With TAFR_CHECKPOINT_INTERVAL=4, the first sync is at the step-4 refresh →
  vLLM path live from step 5.

  Why isn't it done at init? No good reason. At startup the EMA states are just
  initialized to the reference policy (anchor_ema = replay_ema = ref actor
  weights). So the adapters are already well-defined at step 0 — they'd just
  encode "reference policy" until the first EMA update. There's nothing stopping
  us from exporting them once right after tafr_init (ray_trainer.py:1062) and
  flipping tafr_vllm_adapters_ready = True immediately.

  So the "after step 4" behavior is a missed optimization, not a correctness
  constraint. The fix is small: call _tafr_sync_vllm_adapters() once at startup
  (right after the tafr_init at line 1062-1063), so the vLLM fast path is active
  from step 1 — and you'd avoid paying the ~50s HF anchor/replay cost on steps
  1–4 entirely.

  Two ways forward:
  - For your current measurement, the quickest path is
  TAFR_CHECKPOINT_INTERVAL=1 (sync after step 1, vLLM from step 2) — config
  only, no code change.
  - For production, I'd add the one-line startup sync so the fast path is on
  from the first step regardless of checkpoint interval. That's a real,

❯ tafr checkpoint interval =2 means what?                                       

● TAFR_CHECKPOINT_INTERVAL=2 sets
  custom_tafr_grpo.checkpoint_interval_grpo_steps=2, which controls how often
  the TAFR EMA refresh + save cycle runs — every 2 GRPO steps (steps 2, 4, 6,
  …), gated by should_checkpoint_and_refresh(global_step, tafr_config)
  (ray_trainer.py:1245).

  At each of those boundaries, tafr_save_and_refresh (transformer_impl.py:931)
  does three things:

  1. Refresh the EMA reference states — folds the current actor weights into the
  anchor EMA (grpo_ema) and failure EMA (fail_ema) with decay ema_gamma. This
  is what updates the anchor (π_anchor) and replay (π_replay) targets your KL
  terms are measured against.
  2. Save TAFR state to disk — the failure model, its optimizer, and the EMA
  states (tafr/tafr_state.pt). This is the torch.save that crashed when the disk
  was full.
  3. Re-sync the vLLM scoring adapters — _tafr_sync_vllm_adapters() (line 1253)
  re-exports the refreshed anchor/replay as LoRA adapters into vLLM.

  Two important consequences:

  - It gates when the vLLM fast-path first turns on. Since the adapter sync only
  happens inside this refresh branch, with interval=2 the adapters first sync
  at step 2, so the vLLM multi-LoRA scoring path goes live at step 3 (vs step 5
  with interval=4). That's why I suggested interval=2 (or 1) to see the speedup
  sooner.
  - Smaller interval = more frequent EMA updates + more frequent disk saves. So
  the anchor/replay targets track the policy more closely, but you pay the
  torch.save cost more often (every 2 steps instead of every 4).

  Note this is separate from TAFR_SFT_UPDATE_INTERVAL (the failure-SFT schedule)
  and from the trainer's own SAVE_FREQ (actor checkpoint saves) — three
  independent cadences that happen to all be small in our test runs.

● Good question to nail down before changing anything. Two things are involved —
  let me separate them.

  What TAFR_SAVE_FAILURE_OPTIMIZER=false stops saving

  Just one file: failure_sft/optimizer.pt — the Adam optimizer state for the 
  failure-SFT optimizer (_tafr_failure_optimizer). Adam stores, per trainable 
  parameter, two running buffers: the first moment (momentum) and second moment
  (variance). For the failure model that's roughly 2× the parameter count in
  fp32 — it's the single largest TAFR file (bigger than the model weights
  themselves).

  It is not the model. The failure model weights (failure_sft/pytorch_model.bin)
  and the EMA states (tafr_state.pt) are still saved regardless of this flag.

  What would actually happen on resume

  Here's the key fact I found in the code: tafr_load never reads optimizer.pt 
  back anyway (it only restores tafr_state.pt + the failure model weights,
  transformer_impl.py:1039–1053). So:

  - Today (flag=true): the optimizer is written every save but silently ignored
  on resume. It's dead weight — you pay the disk + the ~tens-of-seconds write
  for a file nothing loads.
  - With flag=false: you simply stop writing that dead file. On resume, behavior
  is identical — the failure-SFT optimizer gets re-created fresh (zero
  momentum) either way, because that's what already happens. The failure model
  still resumes from its saved weights; the EMA targets still resume from
  tafr_state.pt.

  The only theoretical cost of starting the optimizer from zero momentum is a
  brief re-warm-up of Adam's adaptive step sizes over a few failure-SFT updates
  — and with failure_sft_lr=5e-7 and very few updates per interval, that's
  negligible. The failure model loses no learned weights.

  What this does not touch

  Critically, this has nothing to do with main training resume. The
  actor/critic/dataloader checkpoints (the real "can I continue training" state)
  are saved and restored by a completely separate path (the actor checkpoint
  manager). Your main GRPO run resumes perfectly whether or not the failure-SFT
  optimizer is saved.

  Bottom line

  - What's never saved: the failure-SFT Adam momentum/variance buffers.
  - What happens: nothing functional changes on resume (because they're already
  never reloaded) — you just stop writing the biggest TAFR file. Main training
  resumability is unaffected.

  The cleaner long-term fix, if you'd rather keep the file meaningful, is to
  make tafr_load actually restore it — then the optimizer momentum survives
  resumes and the file earns its disk cost. Want me to wire that into tafr_load
  instead of dropping it?

  First: you're partly flying blind — fix instrumentation

  The single most useful framework change right now is per-segment timing. This

  The real bottleneck hierarchy (from what we measured)

  Your step is fully serial on one GPU: generate (vLLM awake) → sleep vLLM →
  old_log_prob (FSDP) → ref_log_prob (FSDP) → anchor/replay → actor update →
  wake vLLM. The GPU does one thing at a time, with sleep/wake + KV-cache
  realloc between phases.

  1. Generation is the floor (~110s of ~165s). n=8 samples × 3072 tokens on a
  single colocated GPU. Not cheaply reducible without changing the experiment.
  2. Redundant forward passes are the most addressable waste. Per step you do
  ~4–5 full forwards over the same tokens: rollout logprobs (vLLM) →
  old_log_prob recompute (FSDP) → ref_log_prob → anchor → replay → then update
  fwd+bwd. Several are avoidable.
  3. The TAFR vLLM scoring path isn't engaging — we confirmed
  _tafr_can_score_with_vllm() returns False, so anchor/replay silently run as 2
  extra HF FSDP forwards instead of cheap vLLM prefill.
  4. Save stalls — the +160s 20GB torch.save — already throttled in the current
  run. ✓

  Prioritized fixes (highest leverage first)

  1. Enable bypass_mode → delete the old_log_prob recompute.
  The code already has algorithm.rollout_correction.bypass_mode
  (apply_bypass_mode, ray_trainer.py:2197) that sets old_log_probs = 
  rollout_log_probs. The rollout already returns logprobs; recomputing them on
  FSDP is a whole forward pass you're paying for a tiny accuracy gain. This is
  the biggest easy win (~one full forward removed per step). Trade-off: slight
  policy-ratio bias; usually fine for GRPO.

  2. Actually fix the vLLM anchor/replay scoring (the thing we built but that
